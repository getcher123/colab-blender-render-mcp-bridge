## Ведущий и проверяющие агенты

Только один ведущий агент одновременно меняет notebook, управляет runtime и отправляет изменяющие MCP-запросы. Проверяющим можно поручать чтение локальных копий, отчётов, CSV, patch и выделенных документов. Не давать двум агентам управление одной вкладкой, перезапуском bridge или одним output-каталогом. Перед передачей live-роли сообщить текущую задачу, project root, notebook URL без auth fragment, активный request ID и известный результат.

## Перед любым live-запросом

1. Выбрать правильный root. Новый clone не подключён к очереди существующего MSI автоматически. `mcp_bridge.py` и `mcp_call.py` остаются в корне; vendor cwd находится в `vendor/colab-mcp` даже при `--server`.
2. Прочитать `--status`, проверить свежесть heartbeat и принадлежность PID конкретному executable/project. Исторические PID/port не использовать как конфигурацию.
3. Проверить `active_request`, `inbox`, `processing`, `outbox`. Не повторять неизвестный по исходу запрос.
4. Получить текущий `__list_tools__`, затем `get_cells` и подтвердить URL/содержимое нужного notebook через разрешённый Browser. Успешный bootstrap в чужом scratchpad не разрешает менять рабочий документ.
5. Перед первой записью прочитать актуальные schemas из `bridge_state/tools.json`. Cell IDs из checkpoint подходят только после сверки с текущим snapshot.

Полное восстановление подтверждать свежим успешным smoke, если требуется доказать исполнение. Smoke не должен устанавливать Blender, запускать render или выделять GPU. Для read-only задачи достаточно проверки того слоя, от которого зависит задача; не выполнять smoke ради формальности.

## Очередь и неопределённый исход

- Один stdio `ClientSession` на project root; не создавать отдельную краткоживущую MCP-сессию для каждого запроса.
- `--status` exit 0 ≠ healthy bridge; `--detach` exit 0 = queued only; wrapper `ok: true` ≠ успешное подключение bootstrap. Проверять его вложенный boolean и реальную доступность ячеек.
- Максимальный tool timeout — 600 с. CLI ожидание по умолчанию — 660 с с учётом очереди. Ни истечение CLI, ни ошибка RPC не гарантируют отмену удалённого кода.
- ID уникален. Использовать автоматически генерируемый ID; для повторного чтения — `--result` с фактически выданным ID. Не переиспользовать идентификаторы из evidence.
- Обработка последовательная, но сортируется по имени файла. Порядок зависимых операций обеспечивать ожиданием завершения, а не именами запросов.
- `__shutdown__` не прерывает активный RPC и не очищает pending inbox. Существующий inbox может выполниться при следующем старте. Claimed processing после аварии записывается с `execution_uncertain` и автоматически не повторяется.
- Не удалять очередь или outbox для устранения ошибки. Не выполнять `git reset --hard`/clean в установленном vendor для применения patch.

## Границы доступа и подключения

Использовать подключённый Browser для вкладок и разрешённый локальный терминал/Remote Desktop Commander для процесса. Если Browser context потерян, восстановить его штатно. Не обходить отказ доступа к browser settings через CDP, профили, реестр или другой канал.

Bridge слушает только `127.0.0.1`. Сохранять token/Origin checks и конечный WebSocket limit 16 MiB. Не публиковать auth fragment, access token, cookies, `.env`, raw `bridge_state`, `.venv`, vendor и приватные server logs. Notebook ID и исторический GPU UUID в evidence не являются token подключения.

Новый bootstrap создаёт актуальное браузерное подключение. Не переносить старый auth fragment из истории. `browser.user.openTabs` может показывать открытый upstream scratchpad, которого ещё нет среди управляемых вкладок.

## Новый Blender-прогон

Новый render выполняется только для текущей содержательной задачи пользователя. Для доказательства завершённой A100-цели повторный прогон не нужен. Не менять тариф, не покупать ресурсы и не запускать anti-idle/quota обходы автоматически.

Сначала подтвердить фактическую A100 через GPU guard; выбор accelerator в UI — недостаточное доказательство. По умолчанию `EXPECTED_GPU = "A100"`; альтернативную L4 проверять только как отдельно выбранную задачу с `target_a100_met: false`.

Для нового запуска использовать [производный чистый шаблон](notebooks/Blender_Colab_GPU_Test.ipynb) и [render route](docs/render-and-export.md). Он создаёт уникальный `OUTPUT_DIR` и экспортирует именно его. Не менять только `OUTPUT_DIR` в старом UI notebook: его оригинальный exporter использует жёсткие `output/` paths.

Закреплённые installer/render исходники лежат в `scripts/blender/` и совпадают с embedded источниками шаблона. Изменяя один, согласованно обновить другой и provenance. Прямой default `render_test.py --output-dir` отличается от notebook, поэтому всегда передавать явный каталог.

Успех подтверждать свежим report, PNG/`.blend`, enabled Cycles device, GPU UUID/PID и телеметрией. Различать CPU-подготовку/OIDN и CPU tracing. Сохранять новый результат отдельно, скачать и проверить ZIP/manifest вне временной VM, явно сохранить notebook в Drive и только затем завершать runtime.

## Обновление состояния и передача

После значимого изменения обновить `state.md`: время UTC, что проверено и где, notebook URL без токена, active request ID/результат, артефакты, следующий шаг и оставшиеся неизвестные. Не переписывать историческое evidence под новый путь; новые выводы записывать новым документом с источником.

Перед завершением проверить относительные ссылки, согласованность `config/agent-routes.json` с маршрутом в docs, соответствие code/notebook и отсутствие секретов в добавляемых файлах. Передача считается пригодной, когда следующий агент различает исторический факт, последний checkpoint и ещё не проверенное живое состояние.
