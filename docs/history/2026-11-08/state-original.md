### Три локальные правки vendor

1. **IPv4 loopback.** При `host="localhost"`, `port=0` Windows создавала IPv6 и IPv4 listeners на разных портах, а рекламировался только первый. Default host изменён на `127.0.0.1`; наблюдался один listener.
2. **Отмена startup task.** `wait_for(gather(..., self._start_task), 60)` отменял startup при таймауте. Только `self._start_task` обёрнут в `asyncio.shield`; общее ожидание сохраняет таймаут.
3. **Размер входящего сообщения.** `get_cells(includeOutputs=true)` с PNG закрыл соединение с 1009: следующий фрагмент 49398 байт после 1037772 превысил default 1048576. Добавлен `max_size=16 * 1024 * 1024` в `websockets.serve`, без снятия ограничения и без изменения auth/origin.

Третья правка проверена: `snapshot_full_notebook_20261108_02` завершился в 16:40:26.436 UTC за 0.353 с, сохранён полный ответ 4 549 989 байт, 7 ячеек. PNG из outputs — 1 660 155 байт, SHA256 `5457856705e9146afc7d4c9850a8a5d88de25f72d748ba09eda8511128425abe`. Последующее небольшое `get_cells` успешно за 0.029 с. Файл доказательства: `mcp_large_payload_verification.json`. PNG в этом тесте был историческим L4 результатом; последующая A100 работа шла уже по исправленному каналу.

## Разрешение Chrome и границы доступа

В первой части сессии после ответа пользователя «готово» штатное подключение заработало. Ранее предполагалась Local Network Access / Loopback network блокировка, но точная сетевая причина прежнего сбоя не установлена. Не приписывать тот успех конкретному изменению разрешения без сетевого подтверждения. Текущий blocker — требование исходного браузерного контекста по тексту ошибки; повторная проверка LNA без новой сетевой причины не нужна.

Browser tool отклонил `chrome://settings`, обходы не применялись. При новой ошибке доступа пользователь может проверить разрешение сайта вручную по README. Не обходить отказ через иной транспорт, profile files, CDP или registry.

Не оставлять anti-idle обходы. `/content` временный, после смены VM повторно проверить GPU и установить Blender из закреплённого notebook.
